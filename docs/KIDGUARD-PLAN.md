# KidGuard — แผนสร้างระบบทั้งหมด (รออนุมัติก่อนเริ่มเขียนโค้ด)

> สถานะ: **อนุมัติแล้ว (เจ้าของตอบคำถาม §14 ครบ — ดู §16)** · เริ่มเฟส 0
> Production URL: https://kidguards.vercel.app/ (ยืนยันชื่อโดเมนใน §14 ข้อ 1)
> โรงเรียนแรก: โรงเรียนกรุงเทพคริสเตียน · ออกแบบเป็น multi-tenant สำหรับโรงเรียนอื่นในอนาคต
> Stack: Next.js 16 (App Router, TypeScript) + Tailwind v4 + shadcn/ui · Supabase (Auth + Postgres/RLS + Realtime + Storage) · Vercel (production เท่านั้น)

## 0. สรุปสำหรับผู้บริหาร (อ่านหน้านี้หน้าเดียวก็ตัดสินใจได้)

**ระบบทำอะไร** ผู้ปกครองกด check-in เมื่ออยู่ในรัศมีที่โรงเรียนกำหนด (ค่าเริ่มต้น 2 กม.) → ระบบคำนวณระยะ/เวลาโดยประมาณถึงโรงเรียนต่อเนื่อง →
dashboard ของโรงเรียน (ครู/พนักงานที่คิวส่งนักเรียน) และของครูประจำชั้นเห็นลำดับผู้ปกครองที่กำลังมา เรียงตามเวลาที่จะถึง และ **ลำดับเปลี่ยนสดโดยไม่ต้อง refresh** →
ครู/พนักงานพานักเรียนไปที่รถ → ฝ่ายใดฝ่ายหนึ่งกด "รับแล้ว / check-out" อีกฝ่ายได้รับแจ้งทันที

**ข้อจำกัดทางเทคนิคที่ต้องรู้ก่อนอนุมัติ (ตรงไปตรงมา)**

1. **เว็บแอปติดตามตำแหน่งตอนปิดจอ/พับแอปไปอยู่เบื้องหลังไม่ได้** (ข้อจำกัดของเบราว์เซอร์/iOS ไม่ใช่ของเรา) ผู้ปกครองต้องเปิดหน้าจอ KidGuard ค้างไว้ระหว่างเดินทาง
   เราลดผลกระทบด้วย Wake Lock (กันจอดับ), ตัวบอก "ตำแหน่งเก่า/ขาดสัญญาณ" บน dashboard, และปุ่ม "ฉันถึงโรงเรียนแล้ว" ที่ staff ยืนยันได้
   ถ้าต้องการติดตามเบื้องหลังจริง ต้องทำแอปมือถือ native (นอกขอบเขตแผนนี้ — เป็น Phase ทางเลือกในอนาคต)
2. **ระบบเป็นตัวช่วยจัดคิว ไม่ใช่การยืนยันตัวตน** ตำแหน่ง GPS ปลอมได้ ดังนั้น "ด่านตัดสินสุดท้ายคือคนที่ประตู" — dashboard แสดงชื่อ/ทะเบียนให้เจ้าหน้าที่เทียบกับรถที่มาจริง
   และมีฟีเจอร์ยืนยันตัวผู้รับ (รหัส/QR ครั้งเดียว) เพิ่มใน Phase 6
3. **ETA ที่แม่นยำต้องใช้บริการแผนที่ภายนอก** (มีค่าใช้จ่ายตามการเรียก) — เสนอให้ใช้ตัวกลางที่สลับผู้ให้บริการได้ และจำกัดจำนวนการเรียก (ดู §6.3 และคำถามที่ต้องตัดสินใจ §14)
4. **เพราะใช้ Supabase โปรเจกต์เดียว การทดสอบจะทำบนฐานข้อมูลเดียวกับ production** — ผมจะใช้ข้อมูลทดสอบที่มีคำนำหน้าชัดเจนและลบทิ้งในรันเดียวกันเสมอ, migration ทุกอันเขียนให้รันซ้ำได้ (idempotent) และตรวจก่อนรัน

| เฟส | ชื่อ | ผลลัพธ์ที่ผู้ใช้เห็น |
| --- | --- | --- |

## 2. ฟีเจอร์ที่ผมเสนอเพิ่ม (จากการค้นคว้าระบบรับส่งนักเรียนในไทยและต่างประเทศ)

ที่มาของแนวคิด: ระบบ car-line/dismissal ต่างประเทศ (เช่น PikMyKid, Carpool.School, SDM FastLane, CarpoolArea, Safe Pickup),
ระบบรถรับส่งในไทย/ตะวันออกกลาง (ตัวอย่างโครงงาน Safe Track Bus, MySchoolRide, ระบบรถโรงเรียนของ UAE) และแนวปฏิบัติ PDPA ของไทย (ดูแหล่งอ้างอิงท้ายเอกสาร)

ผมคัดเฉพาะที่เพิ่ม "ความปลอดภัยจริง" และไม่ทำให้ระบบหลักบวม ติดป้าย **[แนะนำ]** = ผมแนะนำให้ทำ, **[ทางเลือก]** = ตัดได้ถ้างบ/เวลาจำกัด

### 2.1 ปกป้องไม่ให้เด็กถูกรับผิดคน (สำคัญที่สุด)

| ฟีเจอร์ | ทำไมสำคัญ | เฟส |
| --- | --- | --- |
| **อนุมัติการผูกนักเรียน–ผู้ปกครอง** — ใครสมัครมาก็ไม่เห็น/ไม่ check-in รับเด็กได้จนกว่าโรงเรียนอนุมัติ (จับคู่กับรายชื่อนักเรียนของโรงเรียน) [แนะนำ] | ถ้าไม่มีข้อนี้ คนแปลกหน้าสมัครแล้วระบุชื่อเด็กคนใดก็ได้ | 2 |
| **รายชื่อผู้มีสิทธิ์รับ (ชื่อ/เบอร์/ทะเบียน/รูปถ่ายถ้ายินยอม)** — A.1 ตามที่ขอ + แสดงให้เจ้าหน้าที่ประตูเทียบ [แนะนำ] | เจ้าหน้าที่เห็นคนและรถที่ลงทะเบียนไว้ | 2–3 |
| **รหัส/QR ผู้รับแทนแบบครั้งเดียว** — ผู้ปกครองสร้างให้ญาติ/คนขับรถที่ไม่ได้อยู่ในระบบ หมดอายุภายในวัน [แนะนำ] | ครอบคลุมกรณีรับแทนฉุกเฉินโดยไม่ต้องเปิดบัญชีเพิ่ม | 6 |
| **ธง "ห้ามปล่อยนักเรียน" (กรณีคำสั่งศาล/ข้อพิพาทสิทธิ์เลี้ยงดู)** — Admin ตั้งได้เท่านั้น ขึ้นเตือนแดงที่ dashboard เมื่อผู้ปกครองที่ถูกห้ามมา [แนะนำ] | ความเสี่ยงสูงและเกิดจริงในโรงเรียน; ข้อมูลอ่อนไหว เข้าถึงได้เฉพาะ Admin | 6 |
| **ขั้นตอนยืนยันที่ประตู** — พนักงานกด "ยืนยันตัวแล้ว" ก่อนเรียกนักเรียน (บันทึกว่าใครยืนยัน) | ตัวควบคุมสุดท้ายอยู่ที่คน และมีหลักฐาน | 3 |
| **เทียบสถานะสองฝั่ง** — ถ้าผู้ปกครอง check-out แล้วแต่ครูยังไม่ยืนยัน (หรือกลับกัน) แจ้งเตือนอีกฝ่าย (D) | จับกรณีกดผิด/เด็กหลงขั้นตอน | 3–4 |

### 2.2 ทำให้คิวลื่นและลดการแออัดหน้าโรงเรียน

| ฟีเจอร์ | หมายเหตุ | เฟส |
| --- | --- | --- |
| สถานะครบวงจร: `on_the_way` → `arrived` (ถึงประตู) → `called` (เรียกนักเรียน) → `picked_up` / `cancelled` / `expired` | ใช้จัดลำดับ + วัดเวลารอ | 3 |
| **เด็กหลายคนในรถคันเดียว (พี่น้อง)** — check-in ครั้งเดียวได้เด็กทุกคน แม้คนละห้อง | ทางโรงเรียนเห็นเป็นหนึ่งแถว ครูแต่ละห้องเห็นเฉพาะเด็กห้องตัวเอง | 3 |
| **หลายประตู/ช่องทาง (zone)** ตั้งค่าโดย Admin; dashboard กรองตาม zone [ทางเลือก] | โรงเรียนใหญ่มีหลายจุดรับ | 6 |
| **หมดอายุ/ยกเลิก check-in อัตโนมัติ** (เช่น 90 นาที หรือเมื่อออกนอกรัศมี) + ปุ่ม "ยกเลิก" | กันคิวผีค้างบน dashboard | 3 |
| **แจ้งล่วงหน้า:** วันนี้รับเอง / ขึ้นรถโรงเรียน / เดินกลับ / ลา-รับก่อนเวลา [แนะนำ] | ลดการแจ้งเตือนที่ไม่เกี่ยวข้อง และครูรู้ล่วงหน้า | 6 |
| **เตือนรับช้า** — เด็กยังไม่ถูกรับเกิน X นาทีหลังเลิกเรียน แจ้งผู้ปกครอง+ครู (ผ่านกฎอัตโนมัติ) [แนะนำ] | ความปลอดภัยของเด็กที่ตกค้าง | 5–6 |
| **ช่วงเวลาเปิด check-in** ต่อวัน (เช่น 14:30–17:30) — นอกช่วงแสดงข้อความอธิบาย | กัน check-in ผิดเวลา | 3 |
| **สถิติคิว** (เวลารอเฉลี่ย, ชั่วโมงแออัด, ผู้ปกครองที่มาช้าบ่อย) ให้ Admin | โรงเรียนปรับเวลาเลิกเรียนเป็นช่วง ๆ ได้ | 5 |

### 2.3 สื่อสาร

| ฟีเจอร์ | เฟส |
| --- | --- |
| **เสียงเรียกชื่อ (Text-to-Speech ภาษาไทย)** ที่จอประตู ตามภาพ "Voice option" — ปิด/เปิดได้ [ทางเลือก] | 6 |
| **จอ TV/เสาธง (โหมดแสดงผลอย่างเดียว)** แสดงเฉพาะชื่อเล่นกับห้อง ไม่แสดงทะเบียนเต็ม เพื่อไม่เปิดเผยต่อสาธารณะ [ทางเลือก] | 6 |
| **ประกาศฉุกเฉิน/พักการรับ** (ฝนตกหนัก, น้ำท่วม, เหตุฉุกเฉิน) Admin ส่งแจ้งผู้ปกครองที่ check-in อยู่ทาง LINE+แอป [แนะนำ] | 6 |
| ปุ่ม "ฉันถึงประตูแล้ว" + ระบุช่องทาง/เลนที่จอด (กรณี GPS ไม่แม่น) | 3 |

### 2.4 ความเป็นส่วนตัว (PDPA) — ไม่ใช่ฟีเจอร์เสริม แต่เป็นข้อบังคับของโครงสร้าง

- **เก็บตำแหน่งเฉพาะตอนมี check-in ที่ active** ไม่มีประวัติเส้นทาง ไม่เก็บพิกัดดิบถาวร (เก็บเฉพาะ ระยะ+ETA ล่าสุด) ตรงกับหมายเหตุของคุณว่าไม่แสดงเส้นทางให้ผู้อื่นเห็น
- ขอความยินยอมแบบชัดเจนก่อน check-in ครั้งแรก (บันทึกเวลา/เวอร์ชันข้อความที่ยินยอม)
- เด็กอายุต่ำกว่า 10 ปี PDPA กำหนดให้ผู้ปกครองให้ความยินยอม — ระบบออกแบบให้ผู้ปกครองเป็นผู้ให้ข้อมูลเด็กทั้งหมด
- หน้านโยบายความเป็นส่วนตัว, ขอดู/ลบข้อมูลตัวเอง, ลบบัญชีแล้วข้อมูลหายตามเกณฑ์ (cascade) + ระยะเก็บรักษา (retention) ที่ Admin กำหนดได้
- ข้อมูลอ่อนไหว (ธงห้ามปล่อย, รูปถ่าย) จำกัดสิทธิ์ที่ระดับฐานข้อมูล (RLS) ไม่ใช่แค่ซ่อนปุ่ม
- ควรให้ที่ปรึกษากฎหมาย/ DPO ของโรงเรียนตรวจข้อความนโยบายก่อนใช้จริง (ผมร่างให้ แต่ไม่ใช่คำปรึกษาทางกฎหมาย)

## 3. บทบาทและสิทธิ์

| บทบาท | ได้มาอย่างไร | เห็น/ทำอะไรได้ |
| --- | --- | --- |
| `parent` ผู้ปกครอง | **เลือกเองได้** (ค่าเริ่มต้นของผู้สมัครใหม่) | ข้อมูลของตัวเอง/บุตรหลานที่ผ่านการอนุมัติ, check-in/out, แผนที่ของตัวเอง |
| `student` นักเรียน (optional) | รหัสผูกที่ผู้ปกครองหรือโรงเรียนออกให้ — **เลือกเองไม่ได้** | เห็นเฉพาะสถานะผู้ปกครองของตัวเอง (ระยะ/เวลา) |
| `teacher` ครูประจำชั้น | Admin กำหนด (ผูกกับห้องเรียน) | dashboard ของห้องที่ตัวเองดูแลเท่านั้น |
| `gate_staff` เจ้าหน้าที่คิวส่งนักเรียน | Admin กำหนด | dashboard รวมของโรงเรียน, เรียกนักเรียน, check-out |
| `school_admin` ผู้ดูแลโรงเรียน | Admin กำหนด | ตั้งค่าโรงเรียน, รายชื่อ, อนุมัติ, audit, แบรนด์โรงเรียน |
| `super_admin` ผู้ดูแลแพลตฟอร์ม | ตั้งด้วยสคริปต์ครั้งเดียว (บัญชีเจ้าของถอนไม่ได้) | จัดการทุกโรงเรียน, แบรนด์แพลตฟอร์ม, feature flags, messaging |

กฎเหล็ก (จาก `docs/SSO-Aivora-Supabase.md` และ `ADMINS-KNOWLEDGE.md`):
- บทบาทที่มีสิทธิ์พิเศษ **ห้ามเลือกเอง** — บังคับที่ **RLS** (ไม่ใช่แค่หน้าจอ): ผู้ใช้เปลี่ยนบทบาทตัวเองได้เฉพาะ `null → parent` ครั้งเดียว
- ผู้ใช้ที่มาทาง SSO ไม่รับ `roles` จาก hub มาใช้กำหนดสิทธิ์
- ทุก action ของ admin เรียก `requireRole()` บรรทัดแรก; หน้า admin ตอบ 404 ให้คนนอก; ระบบต้องไม่เหลือ admin ศูนย์คน
- เลือกใช้ตารางสมาชิกต่อโรงเรียน (`school_members`) เพราะคนเดียวอาจเป็นครูที่โรงเรียนหนึ่งและผู้ปกครองอีกโรงเรียนหนึ่ง

## 4. สถาปัตยกรรม

```
 เบราว์เซอร์/PWA (ผู้ปกครอง, ครู, พนักงาน, นักเรียน)
   │  Next.js 16 (RSC + Server Actions + Route Handlers)  ←→ Vercel (production เท่านั้น, Fluid Functions)
   │
   ├─ Supabase Auth ── Google / อีเมล / Aivora SSO (route แลกตั๋ว ฝั่ง server เท่านั้น)
   ├─ Supabase Postgres + RLS ── ข้อมูลทั้งหมด แยกโรงเรียนด้วย school_id
   ├─ Supabase Realtime ── "ping" ไม่มีข้อมูล → client โหลดข้อมูลใหม่ด้วยสิทธิ์ตัวเอง (Live sync)
   ├─ Supabase Storage ── bucket ส่วนตัว (โลโก้/ไอคอน/รูปผู้รับ) เสิร์ฟผ่าน route ของเรา
   ├─ ผู้ให้บริการเส้นทาง/ETA (ตัวกลางสลับได้) ← เรียกจาก server เท่านั้น
   └─ LINE Messaging API ── webhook ผูกบัญชี + push การ์ด Flex (คิวส่ง + retry)
 Vercel Cron ── งานตามเวลา: หมดอายุ check-in, เตือนรับช้า, ส่งคิว LINE
```

## 5. การ implement A (ลงทะเบียนผู้ปกครอง)

1. สมัคร/ล็อกอิน (อีเมล+รหัสผ่าน, Google, LINE-Aivora) → ถ้ายังกรอกไม่ครบ **ถูกพาไป onboarding wizard ทุกครั้ง** จนครบ (ข้อมูลครบ = ใช้งานต่อได้)
2. Wizard 4 ขั้น (บันทึกทีละขั้น กลับมาทำต่อได้):
   - **A.1 ผู้ปกครอง** ชื่อ, เบอร์โทร (รูปแบบไทย) · เพิ่มได้หลายคน/เบอร์ · **ทะเบียนรถ** (เช่น `กก 1234` + จังหวัด) เพิ่มได้หลายคัน เพื่อกรณีให้คนมารับแทน
   - **A.2 นักเรียน** เลือกโรงเรียน → เลือกชื่อนักเรียนจากรายชื่อโรงเรียน (หรือกรอกชื่อ+ห้องแล้วรออนุมัติ ถ้าโรงเรียนยังไม่ได้นำเข้ารายชื่อ) · เพิ่มได้หลายคน/คนละห้อง
   - **A.3 ครูประจำชั้น** ระบบเติมชื่อครูจากห้องเรียนอัตโนมัติ (ข้อมูลจริงจากโรงเรียน); ถ้ายังไม่ตั้งครูให้ผู้ปกครองกรอกชื่อได้และเก็บเป็นข้อมูลอ้างอิงรอ Admin ยืนยัน
3. สถานะนักเรียนแต่ละคน: **รออนุมัติ → อนุมัติแล้ว** (Admin/ครูประจำชั้นกดอนุมัติ; แจ้งผู้ปกครองทาง LINE/แอป) — check-in ได้เฉพาะ "อนุมัติแล้ว"
4. "ผู้รับแทน": เฟสแรกคือรายชื่อ/เบอร์/ทะเบียนที่ผู้ปกครองหลักเพิ่มและเลือกตอน check-in ว่า "ใครขับ/รถคันไหน"; เฟส 6 เพิ่มรหัส/QR ครั้งเดียวสำหรับคนที่ไม่มีบัญชี
5. ข้อมูลเก่าที่ผู้ปกครองแก้ภายหลังต้อง audit (เปลี่ยนทะเบียน/เบอร์เป็นเรื่องความปลอดภัย)

## 6. การ implement B–D (แกนหลัก)

### 6.1 Check-in (B + C.1)
- ปุ่มใหญ่ "ฉันกำลังไปรับ" → ขอสิทธิ์ตำแหน่ง → **เซิร์ฟเวอร์คำนวณระยะ** (haversine จากพิกัดโรงเรียน; ไม่เชื่อตัวเลขจาก client) →
  ไกลเกินรัศมี (`school_settings.checkin_radius_m`, ค่าเริ่มต้น 2000) → แจ้ง "จะ check-in ได้เมื่อห่างไม่เกิน X กม." (ข้อความอ่านค่าจากการตั้งค่า ไม่ hard-code)
- เลือก: ใครขับ, รถคันไหน, รับเด็กคนไหน (ค่าเริ่มต้น = เด็กทุกคนที่อนุมัติแล้ว)
- ตรวจ: ช่วงเวลา check-in, ความแม่นยำของ GPS (accuracy เกินเกณฑ์ให้ขอใหม่), ไม่มี session ที่ active ซ้อน (unique partial index), rate limit
- GPS ปิด/ถูกปฏิเสธ → อธิบายวิธีเปิด; มีทางสำรอง "ฉันถึงโรงเรียนแล้ว" ให้ staff ยืนยัน (บันทึกว่าเป็น manual)

### 6.2 ระหว่างเดินทาง (C.2)
- client ส่งตำแหน่งทุก ~10–15 วินาที (`watchPosition` + Wake Lock) เฉพาะระหว่าง session active → server คำนวณ ระยะ/ETA แล้วเขียนเฉพาะ `distance_m`, `eta_s`, `eta_updated_at` (ไม่เก็บพิกัด)
- **แผนที่แสดงให้ผู้ปกครองคนนั้นเห็นเองเท่านั้น** (Leaflet + OSM tiles หรือผู้ให้บริการที่เลือก) ส่วน dashboard ทุกแบบ **ไม่เห็นเส้นทาง/พิกัด** เห็นแค่ ระยะ + เวลา (ตามหมายเหตุของคุณ)
- เลิก track อัตโนมัติเมื่อ session จบ/หมดอายุ; ปิดหน้าจอ/หลุดสัญญาณ → dashboard แสดง "ตำแหน่งเก่า X นาที" (ไม่ทิ้งแถวเงียบ ๆ)

### 6.3 ระยะทางและเวลาโดยประมาณ
- ชั้นที่ 1: haversine (ฟรี) ใช้ตรวจรัศมี + ประมาณการเมื่อบริการเส้นทางใช้ไม่ได้
- ชั้นที่ 2: **บริการเส้นทางจริง** ผ่านตัวกลาง `EtaProvider` (สลับ Google Routes / Mapbox / OSRM ได้ด้วยตัวแปร) เรียกจาก server เมื่อ (ก) ผ่านไป ≥ 30 วินาที หรือ (ข) ขยับ ≥ 150 ม. — ลดต้นทุน; ถ้าล้ม → ตกไปชั้นที่ 1 (กฎ fail-open)
- ETA ที่แสดงปัดเป็นนาที; ตัวอักษร "~" เสมอ (เป็นค่าประมาณ)

### 6.4 Dashboard 3 แบบ (C.2.1–C.2.3) + กฎการเรียง
- **เรียงจากใกล้ถึงที่สุด:** `arrived` (ตามเวลาถึง) → ETA น้อย→มาก → ระยะน้อย→มาก; เรียงเอง **ฝั่งฐานข้อมูล/ฟังก์ชัน SQL** เพื่อให้ทุกจอตรงกัน
- **dashboard โรงเรียน (gate_staff/admin):** ชื่อและทะเบียนรถผู้ปกครอง, ระยะ, ETA, ชื่อ+ห้องนักเรียน, สถานะ, ปุ่ม "ยืนยันตัวที่ประตู / เรียกนักเรียน / รับแล้ว"
- **dashboard ครูประจำชั้น:** เฉพาะเด็กในห้องตัวเอง — บังคับด้วย RLS/ฟังก์ชัน SQL (ครูห้องอื่นยิง API ตรงก็ไม่เห็น)
- **dashboard นักเรียน (optional, ปิดเป็นค่าเริ่มต้น):** ระยะ/ETA ของผู้ปกครองตัวเอง + แจ้งเตือนเมื่อใกล้ถึงอีก N นาที (Admin ตั้ง) ผ่านเว็บ/LINE
- ใช้ **ping ตามหัวข้อ**: `school:<id>:queue`, `class:<id>`, `u:<user>` — ping ไม่มีข้อมูล, ฟังเฉพาะสิทธิ์ที่ตรวจที่ฐานข้อมูล; ping ถูกหน่วง (ส่งเมื่อ "ลำดับหรือนาที ETA เปลี่ยนจริง" ไม่ใช่ทุกครั้งที่ GPS ขยับ) เพื่อไม่ท่วมระบบ
- ทางสำรอง: ถ้า WebSocket ต่อไม่ได้ → โพลล์ลายนิ้วมือแบบช้าลงเรื่อย ๆ (ตาม `LIVE-SYNC-KNOWLEDGE.md`) และ **จอ dashboard ที่ประตูไม่ refresh ใต้มือขณะเจ้าหน้าที่กำลังกดปุ่ม**

### 6.5 Check-out (D)
- ผู้ปกครองกด "รับนักเรียนแล้ว" **หรือ** ครู/พนักงานกด "ส่งนักเรียนแล้ว" → ฝั่งใดกดก่อน session จบ (`picked_up`, บันทึก `completed_by_role`) และ **อีกฝ่ายได้รับแจ้งทันที** (แอป + LINE) ตาม D
- กดซ้ำ/กดพร้อมกันปลอดภัย: update แบบ compare-and-set (`where status in (...)`) แล้วนับแถว
- ถ้าฝั่งที่กดทีหลังพบว่าไม่ตรง (เช่น ผู้ปกครองกดรับ แต่ครูยังไม่ได้ปล่อยเด็ก) → ปุ่ม "รายงานไม่ตรง" แจ้ง Admin และบันทึก audit

## 9. การ implement ตามข้อกำหนดของคุณ (ข้อ 8–15)

### 9.1 ล็อกอิน Google และ LINE (Aivora) — ข้อ 8
- **Google:** `supabase.auth.signInWithOAuth({provider:'google'})` + `/auth/callback` (PKCE) — คุณตั้งค่าใน Supabase แล้ว ผมจะตรวจ Redirect URL allow-list ว่ามี `https://kidguards.vercel.app/**` หรือไม่
- **LINE (Aivora) ตาม `SSO-Aivora-Supabase.md`:**
  1. asset path เป็น absolute (Next.js จัดการ แต่ตรวจ `content-type` หลัง deploy ตามเอกสาร)
  2. Route Handler `POST /api/sso/exchange` (server เท่านั้น): แลกตั๋วที่ `https://aivora-lc.netlify.app/api/public/sso/exchange` → ตรวจ `app_slug` → รับ `null` ได้ (`firebase:null` ไม่ใช่ error) → หาผู้ใช้ด้วย `aivora_user_id` (ตาราง `aivora_links`) **ไม่ใช้อีเมลผูกบัญชี** → สร้างผู้ใช้ถ้าไม่มี (อีเมลสังเคราะห์ `aivora+<id>@<โดเมน>` เมื่อไม่มีอีเมล) → `generateLink` + `verifyOtp` ออก session → คืนเฉพาะ `access_token`/`refresh_token`; log ทุก error (ไม่ log token), ใช้ 401/403/502 ให้ถูกความหมาย
  3. หน้า `/sso/callback`: อ่าน `sso_ticket` → **ลบออกจาก URL ด้วย `history.replaceState` ก่อน await ตัวแรก** → แลก → `setSession` (retry เฉพาะ setSession) → **เรียก bootstrap ตรง ๆ ไม่พึ่ง `onAuthStateChange`** → ไม่หมุนค้าง: try/catch + ข้อความจริง + timeout 15 วินาที + `console.info` 6 จุด
  4. ผู้ใช้ SSO ใหม่: role = `null` → หน้าเลือกบทบาท (อนุญาตเฉพาะ `parent`) เป็นหน้าปกติของแอป; RLS WITH CHECK ตาม allow-list; ใช้ RPC `security definer`
  5. ปุ่ม "เข้าสู่ระบบด้วย LINE (Aivora)" → `https://aivora-lc.netlify.app/sso/authorize?app=<slug>&return=<callback>`
  6. ทดสอบตามเกณฑ์ 3 เส้นทาง; **การแลกตั๋วจริงต้องให้คุณกดจากหน้า Launcher** (ตั๋วอายุ 60 วินาที ใช้ครั้งเดียว) — ผมจะรายงานว่าส่วนไหนทดสอบเองได้/ไม่ได้
  7. `grep -ri "service_role\|SUPABASE_SERVICE"` บน build output ต้องว่าง
- **LINE login (Aivora) ≠ LINE OA แจ้งเตือน:** สองอย่างนี้แยกกัน และ LINE userId ที่ได้จาก SSO ใช้ push หาไม่ได้ — การรับแจ้งเตือนต้องผูก OA ด้วยรหัสครั้งเดียว (§9.5) ซึ่งผู้ใช้ที่ล็อกอินด้วยวิธีใดก็ทำได้

### 9.2 Loading spinner ทุกปุ่ม/เมนู — ข้อ 9
กลไกเดียวกันทั้งระบบ ไม่ปล่อยให้แต่ละหน้าทำเอง:
- คอมโพเนนต์ `AsyncButton` / `AsyncLink` / `SubmitButton`: กดแล้ว **แสดงสปินเนอร์ + `disabled` + `aria-busy`** จนงานเสร็จ (รองรับ server action, fetch, การนำทาง); กดซ้ำไม่ได้
- ตัวบอกการนำทางทั้งหน้า (progress bar บาง ๆ ด้านบน) สำหรับเมนู/ลิงก์ที่เปลี่ยนหน้า
- **กฎถูกบังคับด้วยเทสต์/ESLint:** ห้ามใช้ `<button onClick>` ดิบหรือ `<form>` ที่ไม่ผ่านคอมโพเนนต์กลาง; เทสต์ Playwright คลิกปุ่มที่ช้า (หน่วงเทียม) แล้วตรวจว่ามีสปินเนอร์และหายเมื่อเสร็จ
- กรณีพิเศษ (ลูกศรเลื่อนในแผ่นเมนู ฯลฯ) ใช้ `data-nobusy` ตาม `NAVIGATION-KNOWLEDGE.md`

### 9.3 Audit Trail + สวิตช์ — ข้อ 12
- ตาราง `audit_log` เพิ่มอย่างเดียว (trigger ห้ามแก้/ลบ; ลบได้เฉพาะ `admin_purge_audit()` ที่เก่ากว่า 4 ปี และบันทึกการลบ), ไม่มีข้อมูลส่วนบุคคลใน `detail` (เก็บ id/สถานะ/ตัวเลข)
- สองผู้เขียน: server action เรียก `audit()` หลังงานสำเร็จ + trigger ฐานข้อมูลบนตารางสำคัญ (สิทธิ์, ผูกนักเรียน, session, ธงห้ามปล่อย)
- **Admin ปิด/เปิดการเก็บทั้งระบบได้** และ **ติ๊กเลือกชนิด event ที่จะเก็บ** (จัดกลุ่ม: `auth.*`, `pickup.*`, `guardian.*`, `student.*`, `settings.*`, `admin.*`, `channel.*`, `db.*`…) ผ่านหน้า `/admin/audit`; กลุ่มใหม่ที่เพิ่งเคยเกิดจะโผล่ให้ติ๊กเองโดยไม่ต้องแก้โค้ด
- **กฎที่ผมขอเพิ่มเอง:** การเปลี่ยนสวิตช์เองกับการส่งออก/ลบ audit **บันทึกเสมอ ปิดไม่ได้** (ไม่งั้นคนปิดแล้วทำผิดต่อได้โดยไม่มีร่องรอย) — ถ้าคุณไม่เห็นด้วยบอกได้
- ระดับ: ตั้งค่าได้ทั้งระดับแพลตฟอร์ม (super_admin) และระดับโรงเรียน (school_admin เห็นเฉพาะของโรงเรียนตัวเอง)
- ดู/กรอง/ส่งออก CSV (ตัวกรองเดียวกัน), แบ่งหน้าด้วย cursor, เทสต์ครอบคลุมกันลืมเรียก `audit()`

### 9.4 ติดตั้งเป็นแอป (PWA) — ข้อ 14
- `manifest` ไดนามิก (ชื่อ/ไอคอนตามแบรนด์), `display: standalone`, ไอคอน 192/512 + maskable
- Service worker **แคชเฉพาะ `/offline` + ไอคอน** ห้ามแคชหน้าที่มีข้อมูลผู้ใช้ (เครื่องใช้ร่วมกัน)
- เมนู/ปุ่ม "ติดตั้งเป็นแอปบนเครื่อง": Android/Chrome ใช้ `beforeinstallprompt`; iPhone แสดงวิธี Share → Add to Home Screen; ติดตั้งแล้วซ่อนปุ่ม
- ข้อจำกัดที่ต้องบอกผู้ใช้: ติดตั้งแล้วก็ยังติดตามตำแหน่งเบื้องหลังไม่ได้ (ข้อ 0.1)

### 9.5 ผูกบัญชี LINE และการ์ดแจ้งเตือน — ข้อ 13
- ขั้นตอนตาม `LINE-ACCOUNT-LINKING-KNOWLEDGE.md` วิธี A: ผู้ใช้กด "เชื่อมต่อ LINE" → รหัส 8 ตัว (ไม่มี 0/O/1/I, `crypto.randomInt`, เก็บเฉพาะ HMAC, หมดอายุ 30 นาที) → add OA → ส่งรหัสเข้าแชต (ลิงก์ `oaMessage` พิมพ์รหัสให้) → webhook ตรวจ `X-Line-Signature` จาก raw body (`timingSafeEqual`) → ผูกด้วย compare-and-set → หน้าจอ poll เป็น "เชื่อมต่อแล้ว"
- UI 4 ขั้นตอน, ปุ่ม copy / เพิ่มเพื่อน / ส่งรหัส / ยกเลิก / ส่งการแจ้งเตือนทดสอบ (ทุกปุ่มมีสปินเนอร์)
- ปรับปรุงช่องว่างที่เอกสารระบุไว้: **LINE userId หนึ่งตัวผูกได้กับบัญชีเดียว** (unique index), รับ `follow` เพื่อกลับมา active, ตอบเป็นภาษาเดียว, rate-limit ต่อ userId
- การ์ด Flex ตาม `LINE-FLEX-CARD-KNOWLEDGE.md`: หัวเรื่อง + แถว "ป้าย: ค่า" + ปุ่ม "เปิดแอป"; altText ครบ ≤ 400; ตัดทุกช่อง; ลิงก์ภายในเท่านั้น (`?openExternalBrowser=1`); **ไม่ใส่ชื่อเด็กเต็ม/ที่อยู่บนหน้าจอล็อก** ใช้ชื่อเล่น+ห้อง; ภาษาตามผู้รับ
- การ์ดที่จะมี: ผู้ปกครองกำลังจะถึง (ครู/นักเรียน) · นักเรียนถูกเรียกแล้ว · รับแล้ว (อีกฝ่ายกดก่อน) · อนุมัติ/ไม่อนุมัติการผูกนักเรียน · รับช้า · ประกาศฉุกเฉิน · รหัสผ่านถูกเปลี่ยน
- **สิ่งที่คุณต้องเตรียม:** LINE Official Account + Messaging API (Channel secret, access token, Basic ID), ปิด Auto-reply/Greeting, ตั้ง Webhook URL — ผมจะให้คำสั่งทีละขั้น; ควรตัดสินใจเรื่อง **Provider** ตั้งแต่เริ่ม (ย้ายภายหลังต้องให้ผู้ใช้ผูกใหม่ทั้งหมด)

| ตัวจำลอง | LINE push/reply (401/403/400), บริการ ETA ล่ม → fallback |
| หลัง deploy | `curl` ตรวจ content-type asset, header ความปลอดภัย, `grep` service_role ใน build, พิสูจน์ว่า push branch อื่นไม่เกิด Preview |

### 10.2 สิ่งที่ผมทดสอบเองไม่ได้ (จะรายงานชัดเจนทุกเฟสว่าอะไรค้างให้คุณทดสอบ)
Aivora SSO จริง (ตั๋ว 60 วินาที), เบราว์เซอร์ในแอป LINE, ส่ง/รับ LINE จริงบน iOS/Android, GPS จริงในรถ, การติดตั้ง PWA บน iPhone, การใช้งานจริงที่ประตูโรงเรียน

### 10.3 ความปลอดภัยของการทดสอบบนฐานข้อมูลเดียว
ข้อมูลทดสอบมีคำนำหน้า `zz_test_` / อีเมล `@kidguard.test`; สร้างและลบในรันเดียวกัน; ไม่แตะข้อมูลจริงของโรงเรียน; migration ต้องผ่านการอ่านทบทวน + รันซ้ำได้ + มีแผนย้อนกลับ; **แนะนำให้ตรวจแผน Supabase ว่ามี backup/PITR หรือไม่ก่อนมีข้อมูลจริง**

### 10.4 กติกาที่ผมจะบันทึกไว้ใน `CLAUDE.md` แล้วทำตามทุกครั้ง (ข้อ 10–11 และเงื่อนไขของคุณ)

4. ทุกปุ่ม/เมนูมีสปินเนอร์ ผ่านคอมโพเนนต์กลาง

## 11. แผนรายเฟส

> รูปแบบทุกเฟส: ส่งมอบอะไร · ต้องการอะไรจากคุณ · เกณฑ์เสร็จ. **ผมจะหยุดรอคำสั่งของคุณทุกสิ้นเฟส**

### เฟส 0 — รากฐานและการ deploy
- สร้างโปรเจกต์ Next.js 16 + Tailwind v4 + shadcn/ui; ธีมสี/ฟอนต์; i18n ไทย/อังกฤษ; layout + เมนูตามบทบาท (ยังไม่มีข้อมูล) + ปุ่มกลับ
- `AsyncButton`/ตัวบอกการนำทาง + กฎ lint/เทสต์ (ข้อ 9)
- โลโก้/favicon/ไอคอน PWA ค่าเริ่มต้น + manifest + service worker + ปุ่มติดตั้งแอป (ข้อ 14)
- เชื่อม Supabase (client ผู้ใช้ + admin ฝั่ง server), ระบบ migration, ตั้งค่า Vercel (production-only), ตัวแปรสภาพแวดล้อม, headers ความปลอดภัย (CSP ฯลฯ)
- `CLAUDE.md` กติกา + health check + หน้า `/` ขึ้น production ที่ `kidguards.vercel.app`
- **ต้องการจากคุณ:** token (ดู §13) + คำตอบ §14
- **เสร็จเมื่อ:** เปิด URL เห็นหน้าแรกพร้อมโลโก้/favicon/ติดตั้งแอปได้, push branch อื่นไม่เกิด preview, build ไม่มี service_role

### เฟส 1 — บัญชีผู้ใช้และความปลอดภัย
- สมัคร/ล็อกอินอีเมล + Google + LINE(Aivora) ตาม §9.1; ยืนยันอีเมล; ลืม/เปลี่ยนรหัสผ่าน
- `profiles`, `school_members`, RLS + RPC เลือกบทบาท (null→parent), สคริปต์ตั้ง super_admin คนแรก
- Audit Trail แกน (ตาราง, trigger กันแก้/ลบ, `audit()`, สวิตช์ในฐานข้อมูล) — UI อยู่เฟส 5
- **เสร็จเมื่อ:** ผ่านเทสต์ RLS ทั้งสองเคสของ SSO doc; ล็อกอิน 3 เส้นทางผ่าน (ส่วน SSO จริงให้คุณกดทดสอบ)

### เฟส 2 — โรงเรียนและลงทะเบียนผู้ปกครอง (A)
- tenant `schools` + ตั้งค่าโรงเรียนกรุงเทพคริสเตียน (ชื่อ พิกัด รัศมี)
- Admin: ห้องเรียน, ครูประจำชั้น, นำเข้ารายชื่อนักเรียน (CSV), เชิญครู/พนักงาน, อนุมัติการผูกนักเรียน
- ผู้ปกครอง: onboarding wizard A.1–A.3, หลายบุคคล/เบอร์/ทะเบียน/นักเรียน, ความยินยอม PDPA
- **ต้องการจากคุณ:** พิกัดโรงเรียนจริง, ตัวอย่างโครงสร้างรายชื่อนักเรียน/ห้องเรียน (ข้อมูลจริงไม่ต้องส่งตอนนี้ ใช้ข้อมูลสมมุติได้)
- **เสร็จเมื่อ:** ผู้ปกครองสมัครครบจนเข้าหน้าหลักได้; ครูเห็นเฉพาะห้องตัวเอง (พิสูจน์ด้วยเทสต์ RLS)

### เฟส 3 — แกนหลัก check-in → คิว → check-out (B, C, D)
- check-in + รัศมี + GPS + Wake Lock, ETA/ระยะ (§6.3), แผนที่ของผู้ปกครอง
- dashboard โรงเรียน + ครูประจำชั้น + Live sync (ping + สำรอง)
- check-out สองทาง + แจ้งอีกฝ่ายในแอป; หมดอายุอัตโนมัติ; ปุ่ม "ฉันถึงประตูแล้ว"
- **ต้องการจากคุณ:** ผู้ให้บริการ ETA + API key (ดู §14 ข้อ 4)
- **เสร็จเมื่อ:** E2E ผ่านทั้งเส้นทาง และเห็นลำดับสลับสดเมื่อ ETA เปลี่ยน; ทดสอบ GPS จริงโดยคุณ

### เฟส 4 — LINE และการแจ้งเตือน
- ผูก LINE OA (§9.5), `notifyUser` กลาง + คิว + โควตา + retry, การ์ด Flex, ศูนย์แจ้งเตือนในแอป
- แจ้งเตือนสองฝ่ายตอน check-out (D), แจ้งผู้ปกครอง/ครูตามสถานะ
- dashboard นักเรียน + แจ้งเตือน "ใกล้ถึงอีก xx นาที" (C.2.3, ปิดเป็นค่าเริ่มต้น เปิดด้วย flag)
- **ต้องการจากคุณ:** LINE OA credentials + ตั้ง webhook; ทดสอบการ์ดบนมือถือจริง
- **เสร็จเมื่อ:** ผูกบัญชีสำเร็จตั้งแต่ต้นจนจบ, การ์ดมาถึง, error ถาวรทำให้ช่องทาง `stopped`

### เฟส 5 — Admin console เต็มรูปแบบ
- แบรนด์: อัปโหลดโลโก้/ไอคอน/ชื่อแพลตฟอร์ม + **ชื่อและโลโก้โรงเรียน** (ข้อ 5), ผลไปถึงทุกที่ (UI, แท็บ, PWA, LINE)
- หน้า `/admin/audit` (ดู/กรอง/ส่งออก/สวิตช์/ติ๊กชนิด event — ข้อ 12), feature flags, สถิติการใช้งาน+คิว, กฎอัตโนมัติ (เวลา/ตัวเลขปรับได้), จัดการแอดมิน
- **เสร็จเมื่อ:** เปลี่ยนชื่อ/โลโก้แล้วเห็นภายใน ~1 นาที ทุกจุด; ปิดกลุ่ม audit แล้วไม่มีแถวกลุ่มนั้นเข้ามา

### เฟส 6 — ฟีเจอร์ความปลอดภัยเพิ่มเติม (เลือกได้ทีละรายการ)
รหัส/QR ผู้รับแทน · ธงห้ามปล่อย · เตือนรับช้า · แจ้งล่วงหน้า (รับเอง/รถโรงเรียน/ลา) · เสียงเรียก (TTS) · โหมดจอ TV · หลายประตู (zone) · ประกาศฉุกเฉิน/พักการรับ

### เฟส 7 — Hardening และนำร่องจริง
ทบทวนความปลอดภัย (`/security-review`, RLS audit ทุกตาราง, rate limits, CSP), ทดสอบโหลด (ผู้ปกครองพร้อมกันหลายร้อยคนช่วงเลิกเรียน — ตรวจโควตา Realtime/การเชื่อมต่อของแผน Supabase), ทดสอบเครื่องจริง iOS/Android + LINE in-app browser, หน้านโยบาย PDPA, เอกสารฝึกอบรมครู/พนักงาน, ขึ้นใช้งานจริงแบบ soft launch (1–2 ห้อง) ก่อนเปิดทั้งโรงเรียน

## 14. คำถามที่ต้องการให้คุณตัดสินใจ (ผมใส่ค่าที่แนะนำไว้ ตอบ "ตามที่แนะนำ" ได้เลย)

## 18. บันทึกการทำงานจริง เฟส 3–4

### เฟส 3 — check-in → คิว → check-out (B, C, D)
- **ระยะ/ETA:** server คำนวณเอง (ไม่เชื่อตัวเลขจาก client) · รัศมี/ช่วงเวลา/อายุ check-in อ่านจากการตั้งค่าโรงเรียน ไม่ hard-code · Google Routes เรียกเมื่อเริ่มและทุก ≥ 30 วินาที (ลดต้นทุน) ระหว่างรอบปรับตามสัดส่วนระยะเส้นตรง · ไม่มีคีย์/เกินเพดานรายวัน (`ETA_DAILY_CAP`, ค่าเริ่มต้น 20,000)/Google ล้ม → ประมาณจากเส้นตรง (ระบบไม่พัง)
- **ความเป็นส่วนตัว:** ไม่เก็บพิกัด/เส้นทาง (เก็บเฉพาะระยะ+ETA+ตัวเลขช่วยลดการเรียก API) · เส้นทางส่งให้ผู้ปกครองเจ้าของเท่านั้น วาดบนแผนที่ของเขาเอง · แผนที่ใช้ Leaflet + ภาพจาก OpenStreetMap (เหมาะระดับโรงเรียน; ถ้าใช้หนักควรเปลี่ยนผู้ให้บริการภาพแผนที่ตามนโยบายของ OSM)
- **คิว:** เรียง ถึงประตู → ETA น้อย→มาก → ระยะ ที่ฟังก์ชันฐานข้อมูลตัวเดียวเพื่อให้ทุกจอตรงกัน · พี่น้องคนละห้องในรถเดียว = 1 แถว · ครูเห็นเฉพาะเด็กห้องตัวเอง (บังคับที่ฐานข้อมูล) · เด็กหนึ่งคนอยู่ในคิวที่ยังไม่จบได้ครั้งเดียว
- **ปิดงานได้ทั้งสองฝั่ง (D):** ผู้ปกครองกด = จบทั้งคิว; เจ้าหน้าที่ประตู/แอดมิน = ทั้งคิวหรือรายคน; ครู = เฉพาะห้องตัวเอง (เมื่อเด็กคนสุดท้ายถูกปล่อย คิวจบเอง) — compare-and-set กันกดซ้ำ
- **Live sync:** Realtime private channel ส่ง ping ไม่มีข้อมูล, นโยบายผู้ฟังอยู่ที่ฐานข้อมูล (`live_may_hear`), token ผ่าน `/api/live/token`, ทางสำรอง polling ลายนิ้วมือ · **พบและแก้ช่องโหว่ของแบบเดิมในเอกสาร knowledge:** baseline ที่ client ถามครั้งแรกอาจ "ใหม่กว่า" ข้อมูลบนหน้า (ถ้ามีการเปลี่ยนระหว่าง render กับถามครั้งแรก) ทำให้หน้าค้างเก่า → ตอนนี้ server ส่งลายเซ็น ณ ตอน render (คำนวณก่อนอ่านข้อมูล) เป็น baseline
- **งานตามเวลา:** Vercel Cron ทุกนาที (`/api/cron/tick`, ต้องมี `CRON_SECRET`) หมดอายุ check-in ที่ค้างและแจ้งผู้ปกครอง
- **ตัดออกไปก่อน (ตามแผน เฟส 6):** เสียงเรียก, จอ TV, หลายประตู, รหัส/QR ผู้รับแทน, ธงห้ามปล่อย, เตือนรับช้า, แจ้งล่วงหน้า, ประกาศฉุกเฉิน

### เฟส 4 — LINE และการแจ้งเตือน
- **OA แยกต่อโรงเรียน (ตามที่ตัดสินใจ):** แต่ละโรงเรียนใส่ Basic ID / Channel secret / Access token ที่ `/admin/line` — ความลับเข้ารหัส AES-256-GCM ด้วยกุญแจ `APP_ENCRYPTION_KEY` (env ของ Vercel) ในตารางที่ client เข้าถึงไม่ได้ และไม่แสดงกลับ/ไม่เข้า audit · Webhook ต่อโรงเรียน `/api/line/webhook/<slug>`
- **ผูกบัญชี (LINE-ACCOUNT-LINKING):** รหัส 8 ตัว (ไม่มี 0/O/1/I, `crypto.randomInt`) เก็บ HMAC ผูกกับโรงเรียน หมดอายุ 30 นาที · ตรวจลายเซ็นจากไบต์ดิบ · จำกัด 10 ครั้ง/10 นาทีต่อ LINE userId · คำตอบรหัสผิด/หมดอายุ/ซ้ำเหมือนกัน · LINE userId หนึ่งตัวผูกได้กับบัญชีเดียวต่อโรงเรียน (ทำตามช่องว่างที่เอกสารแนะนำ) · รับ `follow`/`unfollow`
- **การ์ด Flex (LINE-FLEX-CARD):** ตัดทุกช่องตามขีดจำกัด, altText มีรายละเอียดในตัว, ลิงก์ภายในเท่านั้น + `openExternalBrowser`, สีตามชนิด, **ชื่อเด็กใช้ชื่อเล่น/ชื่อต้น + ห้อง ไม่ใส่นามสกุล** (ขึ้นหน้าจอล็อก)
- **ตัวส่งกลาง `notifyUser`:** กล่องแจ้งเตือนในแอป (กระดิ่ง + `/notifications` อัปเดตสด) + LINE ถ้าผูกไว้ · dedupe ต่อเหตุการณ์ · โควตารายเดือนของเรา · 400 → ข้อความธรรมดา (ไม่หยุดช่องทาง), 400 ซ้ำ → ช่องทางผู้ใช้ `stopped`, 401/403 → หยุดทั้งโรงเรียน 6 ชม. + แจ้งผู้ดูแล, 5xx → ลองซ้ำหนึ่งครั้งด้วย retry key เดิม · **ต่างจากเอกสาร:** ไม่มีคิวส่งแบบตาราง (ส่งทันทีหลังตอบผู้ใช้ด้วย `after()` + retry หนึ่งครั้ง) — พอสำหรับปริมาณของโรงเรียนเดียว ถ้าปริมาณสูงค่อยเพิ่มคิวใน `message_log`
- **เหตุการณ์ที่แจ้ง:** ผู้ปกครองกดรับก่อน → เจ้าหน้าที่คิว+ครูของเด็กในคิว · เจ้าหน้าที่/ครูกดก่อน → ผู้ปกครอง · เรียกนักเรียน → ผู้ปกครอง · หมดอายุ → ผู้ปกครอง · อนุมัติ/ไม่อนุมัติคำขอผูกนักเรียน → ผู้ปกครอง · ใกล้ถึง (ETA ≤ N นาที ที่ Admin ตั้ง) → บัญชีนักเรียน
- **นักเรียน (optional, ปิดเป็นค่าเริ่มต้น):** ลิงก์ครั้งเดียวจากผู้ดูแลโรงเรียนหรือผู้ปกครองที่ได้รับอนุมัติ → จอ `/student` เห็นเฉพาะ ระยะ/เวลา/สถานะ (ไม่เห็นชื่อผู้ปกครอง ทะเบียน ตำแหน่ง เส้นทาง) · โรงเรียนเปิดใช้ที่ `/admin/settings`
